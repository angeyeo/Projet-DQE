# T24 Phase 4C — Matrice de couverture du contrat API

État audité localement, puis finalisé en phase 4C après les phases 4, 4B et 4C. Les chemins et méthodes viennent des schémas `api.legacy_urls` et `api.v1_urls`; les deux préfixes pointent vers la même implémentation métier.

Après intégration sur `dev`, les schémas courants exposent 62 chemins et 86 opérations par version. Les sept opérations récentes sont couvertes par des scénarios nominaux sous `/api/v1/`, en plus des tests legacy existants. Les parcours de structure et de note de calcul utilisent le moteur réel ; les fonds DXF sont des fixtures synthétiques, sans fichier client.

« Couvert » exige un scénario nominal exercé sur legacy et v1, les contrôles de sécurité applicables et, pour les mutations, une vérification de l’effet en base de test. « Partiel » conserve une lacune vérifiable (parité nominale incomplète, forme de réponse ou cas métier non testé). Les contrôles transversaux ne sont pas assimilés à des tests nominaux.

## Réponses, paramètres et uploads

- Les paramètres de chemin sont obligatoires dans les deux schémas. Les filtres `projet`, `lot`, `q` et les paramètres `export` sont déclarés; les valeurs `pdf`, `excel`, `dxf` sont énumérées selon la route. `POST generer-dqe/` accepte aussi un corps JSON facultatif `{export: pdf|excel}`, en plus du query param.
- Les opérations protégées exposent maintenant les réponses JSON d’erreur 401/403; les chemins de ressource exposent 404; les écritures exposent 400. Les erreurs spécifiques restent déclarées par les vues (428 T12, 429 throttling, 502/503 service/import).
- Import IFC/DXF : multipart fichier et JSON pour la confirmation/sélection. Vision et import Excel : multipart fichier uniquement. Les exports DQE PDF/Excel, plan PDF/DXF et approvisionnement Excel sont documentés comme binaires avec leur type MIME.
- Les réponses de succès ne sont pas enveloppées par `error`. Les schémas ne contiennent aucun exemple de données, client ou secret.

## Routes historiques et recommandation

- `/api/token/`, `/api/token/refresh/`, `/api/token/verify/` et `/api/me/` coexistent avec les routes `/api/auth/...`; React utilise les routes `/api/v1/auth/...` et `/api/v1/me/`.
- Les aliases DQE `generer-dqe/` et `generer_dqe/` appellent la même action et ont des `operationId` distincts. Garder les deux pour l’instant. La décision de retrait nécessite une mesure des consommateurs externes et l’accord du chef de projet et du responsable Django; aucune route ni date de retrait n’est modifiée ici.
- Les deux couples schema/docs sont uniquement montés avec `DEBUG=True`. Le passage en production nécessite de vérifier que `DEBUG=False` est forcé et que CORS, JWT, tailles d’upload, stockage des médias, et entêtes `Content-Disposition` sont correctement configurés sur l’hébergement cible.
- Aucun retrait de route n’est recommandé avant la coordination T15 (#74).

## Résultat de l’audit ligne par ligne — Phase 4C

La matrice de Phase 4B comptait 30 lignes partielles après ses premiers compléments. Chaque ligne a été réévaluée en Phase 4C et reliée à un test d’opération exact sur les deux préfixes. Les tests de sécurité paramétrés ajoutés couvrent, pour chaque opération protégée, le refus anonyme; pour les routes avec identifiant de ressource des familles multi-tenant listées dans le test, ils couvrent le 404 inter-cabinets sans mutation; les restrictions de rôle sont testées explicitement sur les opérations sensibles ciblées. Les routes publiques sont indiquées non applicables pour le test anonyme. Les réponses 401/403 ne remplacent pas le scénario nominal.

Les 30 opérations précédemment partielles disposent maintenant d’un scénario nominal sur les deux préfixes, et les mutations vérifient leur effet réel en base de test ou leur invariance attendue. Les refus anonymes, les rôles insuffisants et l’isolation cabinet restent référencés séparément; ils ne sont pas déduits du seul scénario nominal.
